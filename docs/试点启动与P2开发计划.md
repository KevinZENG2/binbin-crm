# 试点启动与 P2 开发计划

2026-10-13，适用于当前 v0.6 云测试。产品属于你，由你向多家企业提供订阅服务；继续在云端开发，不部署到你的服务器。

## 本轮状态与进入条件

|事项|本轮完成|实际完成还需要|
|---|---|---|
|备份保留|已部署 30 天保留规则，保护至少最近 3 份成功备份；15 项运维测试通过|下一次实际定时执行确认新规则；不把部署就绪当作执行成功|
|独立密钥保管|RSA 公钥加密恢复包工具、离线恢复工具和失败检查已完成|你的公钥或独立密钥库位置，完成实际交接及离线解封验证|
|正式邮件|已核对 Resend SMTP 接入方式，提供配置表、TLS / 认证检查工具，应用增加证书主机名校验|邮件服务账号、已验证发信域名、发件地址、私有 API Key 和指定测试收件地址|
|客户试点|开通路径、角色分工、验收表和退出流程已准备|真实企业及管理员资料、业务样本和客户参与后的验收反馈|
|P2|子阶段、业务规则、技术依赖和验收标准已整理|以上三项交接、真实邮件和试点验收通过后，再开始 P2-A 实现|

备份定时保持每天北京时间 02:00，UTC 表达式为 `0 18 * * *`。本轮没有通过改时间或取消计划来强行触发任务；“临时取消定时计划”被自动审批拒绝后，保持原计划。当前连接工具没有手动 cron 运行能力，CLI 也未安装。下一次计划时间为 2026-10-14 02:00（可能有几分钟偏差）。

本轮云主应用 Java 32 项、运维 15 项及发布后的 HTTPS 63 项只读验收通过；前端 TypeScript / Vue 构建通过。只读验收核对备份可用标记、不泄露私有地址和 3 个构建资源哈希。没有重新执行完整业务写入验收，也没有浏览器视觉 / 鼠标端到端验收。详见 `运维增量验收.json`。

## 一、备份与密钥交接

保留规则：保留完成时间在最近 30 天内的成功备份，同时始终保护最近 3 份成功备份；不足 3 份时保留全部。超过 30 天且不在保护范围内的对象，只在新快照完成上传、回读、认证解密、篡改拒绝和独立数据库恢复之后清理。

清理核对 `sys_job_run` 中成功快照的 UUID、时间、对象目录、大小和 SHA-256 元数据。保护对象缺失、候选对象元数据异常或删除未确认时停止清理。只处理 `backups/preview/` 下匹配任务 UUID 的 `.snapshot.aesgcm` 文件，不列举全桶删除，不处理附件目录。未登记或失败的快照对象不自动清理，需单独核对。删除后仅清空该任务的文件引用；任务、校验摘要和大小继续保留用于审计。中断后重跑可识别已删除的过期文件，不重复删除。

`DATABASE_BACKUP` 和 `BACKUP_RETENTION` 是两个结果：快照成功、清理失败时，保留快照的成功状态，并记录清理失败。平台运营进入「平台运维」查看这两类任务与恢复文件的保留状态。当前只在同一 Railway 项目的私有桶保存快照，尚未建立跨账号或异地副本。

密钥现有唯一运行副本在备份服务 `crm-db-bootstrap` 私有变量 `CRM_BACKUP_ENCRYPTION_KEY`，继续保留以恢复旧快照。本轮不轮换、不打印、不在源码或聊天保存明文。

推荐离线交接步骤：

1. **你在自己的设备上**运行下列命令，输入私钥口令；私钥和口令由你保管。不要在云端执行私钥生成，也不要发送私钥。

   ```bash
   openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:3072 -aes-256-cbc -out crm-custody-private.pem
   openssl pkey -in crm-custody-private.pem -pubout -out crm-custody-public.pem
   ```

2. 只提供 `crm-custody-public.pem` 的公钥文本。产品运维用此公钥，在持有当前备份密钥的受控任务中运行 `server/ops/backup_key_custody.py wrap`，生成 RSA-OAEP-SHA256 加密的恢复包。公钥指纹和备份密钥摘要用于核对身份与完整性，不包含明文密钥。
3. 将加密恢复包交付给你，在独立于 Railway 项目的受控位置保存；私钥保存在你自己设备或独立密钥库。两者共同可恢复密钥，应分开放置并记录责任人。
4. 你在自己的设备安装 Python `cryptography` 后进行离线验证；口令通过交互输入，恢复的明文密钥只写入你指定的新本地文件（0600），不输出到终端，不发送给我。

   ```bash
   python3 server/ops/backup_key_custody.py unwrap --packet crm-key-recovery.json --private-key crm-custody-private.pem --output crm-recovered-key.txt
   ```

5. 验证恢复摘要一致，再记录保管人、位置、交接日期和验证日期。恢复文件验证后安全处理，不随项目、截图或网盘公共链接传播。当前测试只用一次性随机密钥证明加密 / 解封能力，**尚未完成现有真实备份密钥的独立交接**。

跨账号快照副本和外部告警后续再接入；独立密钥保管不能代替快照本身的异地副本。

## 二、正式邮件接入

建议先使用 Resend 的事务邮件 SMTP。它支持现有 JavaMail 实现，当前官方文档要求 API Key 与已验证域名。服务账户和域名验证由你提供或在你指定的服务账户完成；当前未创建服务账户、购买套餐或修改 DNS。

官方参考（2026-10-13 核对）：

- SMTP：https://resend.com/docs/send-with-smtp
- 域名验证：https://resend.com/docs/dashboard/domains/introduction

|Railway 主应用变量|推荐配置|说明|
|---|---|---|
|CRM_SMTP_HOST|smtp.resend.com|主机|
|CRM_SMTP_PORT|465|隐式 TLS|
|CRM_SMTP_USER|resend|固定用户名|
|CRM_SMTP_PASSWORD|你的受限发信 API Key|只填 Railway 私有变量，不能填在聊天或源码|
|CRM_SMTP_FROM|你已验证域名的发件地址|例如 `crm@你的域名`；示例不能直接使用|
|CRM_SMTP_SSL|true|证书及主机名校验|
|CRM_SMTP_TLS|false|465 使用 SSL；若改 587 则 SSL=false、TLS=true|
|CRM_PUBLIC_BASE_URL|https://crm-java-api-crm-test.up.railway.app|当前真实 CRM HTTPS 来源；以后切正式域名时同步更新|

操作位置：[Railway 主应用 → Variables](https://railway.com/project/1807b9ed-791a-4e66-b77a-890d6b802621/service/5de432e5-b90a-4f2e-ae7c-149619956985?environmentId=415d5c14-f4c6-418f-8387-019e6cb1f14c)。保持测试 / 正式配置分离，不把 Resend 密钥加到前端构建变量。

启用前依次验收：

1. 邮件服务后台确认你控制的域名已验证，发件地址属于该域名；记录服务和发件地址，不记录 API Key。
2. `server/ops/check_smtp.py` 在私有变量环境运行，验证 TLS 和 SMTP 认证。它不发送邮件；检查失败只输出固定错误，不暴露凭据。当前尚未对真实服务运行此检查。
3. 用你明确指定的自己测试邮箱核验归属，再由平台运营进入「登录账号 → 绑定找回邮箱」。绑定会撤销该账号旧会话，提前准备重新登录。
4. 在登录页申请一次找回，检查实际到达、链接 HTTPS、30 分钟有效、使用后失效与原会话撤销；记录实际投递耗时及垃圾箱情况。只有指定收件人和测试范围明确后才发送，不主动联系客户。
5. 至少验证 SMTP 故障的固定提示和失败任务记录；失败链接不可继续使用。真实 SMTP 失败不应导致泄露账号是否存在。

当前真实邮件找回仍关闭。SMTP 握手成功不等于邮件送达；服务接入完成也不等于客户邮箱归属已核验。

## 三、首家客户试点

建议先一家企业、14 天、1 位管理员兼经理、2 位销售、1 位只读成员。期限和人数是建议，取得真实资料后再建立，不占用现有示例企业或冒用真实人员身份。

开通需你提供：企业名称、企业唯一编码（可由运维生成并核对）、管理员登录名 / 姓名、试用天数、目标套餐。初始密码通过平台私密创建流程生成并由你交付，首次登录强制改密；不通过聊天索取客户现有密码。账号邮箱须单独核验。

|顺序|在哪里操作|操作人|验收记录|
|---|---|---|---|
|1. 开通企业|平台运营 → 企业与订阅 → 开通企业|你 / 产品方运营|企业、套餐、额度、管理员和到期时间准确|
|2. 设置组织|企业管理 → 部门管理 / 组织成员|客户管理员|经理、销售、只读成员角色与部门正确|
|3. 核对权限|企业管理 → 角色权限；客户 → 共享 / 转交|客户管理员与销售|自己的客户、部门范围、共享 / 撤销、敏感字段符合实际需要|
|4. 导入样本|CRM → 导入导出 → 客户导入|客户管理员兼经理|先 10～20 条脱敏样本，核对错误行、负责人及防重复；不直接导入大批真实客户|
|5. 走完整销售流程|线索 → 转客户；联系人、商机、跟进、待办|客户销售|至少 3 条业务路径；包括成交和丢单各一条|
|6. 报表与附件|数据报表、附件、站内提醒|客户负责人 / 销售|金额和日期口径、文件权限、容量、待办提醒与原记录一致|
|7. 登录恢复|平台登录账号绑定；登录页找回|你与指定测试用户|真实邮件送达和恢复链路通过，保留隐私化证据|
|8. 运维演练|平台运维与隔离恢复实例|产品方运营|每日任务、保留规则、独立密钥解封和恢复结果可核对|
|9. 试点反馈|本文件下方验收表|客户负责人|设备体验、阻断缺陷、业务差距、可接受限制与是否继续|

试点记录表（真实客户尚未填写）：

|项目|待填内容|
|---|---|
|企业 / 验收人 / 试点日期|待客户资料|
|设备与浏览器|桌面 / 手机及实际版本|
|权限与业务流程结果|通过 / 失败 + 复现步骤|
|报表对账、附件、提醒|源记录及差异|
|邮件到达与独立恢复|日期、耗时、脱敏结果|
|阻断缺陷及负责人|缺陷编号、影响、修复验证|
|客户是否接受当前限制|明确反馈及下一轮需求|

退出条件：租户隔离、账号安全、权限或金额错误均视为阻断；先修复再继续。试点中只支持固定角色和销售阶段、客户 CSV 导入、单文件 5MB、六类导出最多 5000 条、站内提醒、人工续费。未承诺 AI、电子签章、在线支付或自定义流程。

若客户停止试点，平台运营暂停该企业，保留业务资料和审计；暂停不是删除，也不是立刻释放其历史备份。数据导出或删除应由客户明确要求后另执行。备份 30 天政策不等于客户停用数据的删除政策。

## 四、P2 分阶段开发

P2 解决客户企业自己的销售交易：产品、报价、审批、合同及回款。你向客户收取的 CRM SaaS 订阅费继续使用现有订阅模块，双方账务不会混用。下列方案为开发基线；没有把这些能力标为已经上线。

|子阶段|用户能完成的操作|主要实现|完成标准|
|---|---|---|---|
|P2-A 产品与报价|维护产品 / 服务价目，客户 / 商机关联报价，明细、折扣、有效期、版本和 PDF 导出|产品目录、报价及行项目；人民币整数分、数量定点值；快照价目和明确舍入；草稿 / 提交 / 作废|金额重算一致、修改版本冲突可见、重复请求只产生一份、停用产品不改变历史报价、跨企业不可读写|
|P2-B 报价审批|提交后由指定销售经理批准或驳回，查看审批记录；变更需重新提交|初期单级指定审批人；审批请求保存报价版本、金额和规则快照；提交人不可自审；锁定并发决策|非审批人无法操作、旧版本不可审批、重复批准幂等、驳回原因完整、到期 / 作废不可转合同|
|P2-C 合同|由已批准报价建立合同，保留报价与客户快照、附件和变更历史，登记签订 / 生效 / 终止|合同与收款计划，复用私有附件；有效期、履约状态和审计；金额变化重新走受控变更|报价与合同关系可追溯、合同编号企业内唯一、未批准报价不可建合同、合同附件受权限和容量约束|
|P2-D 回款|登记合同到账、核对计划、查看已收 / 待收 / 逾期；错误回款通过冲正纠正|到账登记及确认、冲正链、并发额度校验、银行凭证附件；按合同汇总；人工核对|已确认回款才计入、重复凭证 / 请求防重复、不超合同可收余额、冲正不删除原记录、对账和导出一致|

初期合同为业务登记，不包含外部电子签章、发票系统或法律效力验证；回款为人工到账登记，不接管银行或支付网关。PDF 导出需做分页、长明细和中文字体视觉验收。

共同技术要求：

- 延续 Java 21 / PostgreSQL / Vue、租户上下文、强制 RLS、版本锁、幂等和审计。企业管理员仅管理组织，不自动取得销售交易或审批权；新增报价、合同、回款读写和审批权限。
- 批准后的报价、签订合同、已确认到账采用快照和受控变更，不能直接修改历史金额。人民币金额使用整数分，百分比与数量使用定点值，服务器按统一舍入规则重算，禁止浮点金额。
- 对新建 V6 及后续迁移，先升级备份 / 恢复的版本和 RLS 表校验。现有工具按 V1～V5 / 17 张 RLS 表验证，不能直接迁移新业务表后继续沿用固定数目；应按已知迁移版本验证预期表集合、强制 RLS、属主和运行账号隔离，并补全完整恢复验收。
- 所有写入验收在新建隔离原生 PostgreSQL 数据库和虚构业务中进行，原云预览只做必要发布、真实试点开通与经授权的实际业务操作。测试套件不能拿客户企业当隔离测试库。
- 每个子阶段交付：线上可预览入口、新增 / 修改 / 未实现内容、隔离与只读在线验收、用户操作路径、下一步。正式 SMTP、密钥交接和真实客户试点通过前，P2 保持计划状态。

P2-A 起步顺序：确认试点反馈 → 扩展权限和迁移 → 升级备份恢复版本校验 → 产品目录 → 报价草稿 / 明细 → 报价版本和 PDF → 隔离验收 → 云预览交付。审批、合同和回款在后续子阶段完成。
