# P2-C / D 合同与回款开发交付

开发版本 v0.10.0，2026-10-14（北京时间）。本轮合并交付 P2-C 合同和 P2-D 回款，继续提供云测试预览，不接入用户服务器。

## 在哪里操作

打开 [客户企业端](https://crm-java-api-crm-test.up.railway.app/?account=owner)，沿用原测试账号密码登录，选择“星澜科技 · 测试企业”。顶部新增“合同管理”“回款管理”“收款对账”。owner 是企业管理员加销售经理的体验账号，alice 是销售账号。企业管理员角色本身仅负责组织和权限，业务角色另行授予。

|操作|入口|使用人|
|---|---|---|
|建合同|合同管理 → 从批准报价建合同；批准报价详情 → 建立合同|获准销售 / 经理，且可写入所属客户和商机|
|编辑草稿、签订 / 生效、终止|合同管理 → 查看 → 对应操作|合同写入范围内的销售 / 经理|
|受控变更|合同详情 → 受控变更，选择同客户、同商机的新批准报价|另获合同变更权限的销售经理|
|分期计划、商业快照、历史、合同文件|合同详情|具备合同及上级资料读取权限的成员|
|登记回款|回款管理 → 登记回款，选择已签订合同及期次|拥有回款登记权限的销售 / 经理|
|上传到账凭证|回款详情 → 附件 → 上传；确认时选择凭证|另有附件权限的登记人 / 获准经理|
|确认到账|回款详情 → 核对并确认到账|另有确认权限、与登记人不同账号的销售经理|

平台运营端供产品方开通企业、管理套餐、订阅、账号及运维，不自动取得客户企业的合同或回款正文。限时支持授权继续仅包含客户只读。流程演示端使用浏览器虚构数据，本轮新增业务在真实客户企业端操作。

## 合同管理

合同必须以当前有效、已批准的报价及其版本、金额、审批快照为依据。系统生成 CT 编号，保存客户、公司、商机、报价人及产品明细快照，金额不能通过请求自行指定。收款计划最多 24 期、每期金额大于零，合计必须等于合同含税总额。

合同状态为草稿、已签订、履行中、已终止、已作废。签订后不能直接改写或作废；变更需引用同一客户 / 商机的新批准报价，并填写原因。旧报价、计划和合同版本继续保留。已收期次、有待确认回款的期次不能移除；变更后合同总额和期次金额不能低于相应净已收。终止保留未结应收，并继续允许核对和收款。

一个批准报价版本仅消费一次。关联未作废合同的报价不能转回草稿或直接作废；调整应新建报价并重新审批。合同草稿作废仍保留原版本的引用历史。

## 回款与对账

登记生成 RC 编号，保存到账日期、银行凭证号、付款单位、银行、期次和金额。待确认登记不计入已收。银行凭证号在本企业内按去空格、大小写及全角字符归一化防重复。确认需由另一账号、另获授权的经理完成，并再次检查合同与期次余额，并发确认不会超收。

已确认回款不能直接改写或删除。冲正生成独立 RV 编号，支持部分 / 全额，保留原因、日期、操作人与原记录。全额冲正后可建立关联原回款的更正登记，再核对确认，不允许更正链分叉。冲正只纠正 CRM 账务，不会向银行发起退款。

当前净已收为确认到账减冲正；未收为合同金额减净已收；逾期按今天之前到期的未结期次计算。期间到账 / 冲正按各自业务日期统计，与当前余额分开显示。对账日期最多 367 天，金额按整数分保存，汇总使用精确数字字符串，前端按 BigInt 显示。CSV 遵循相同筛选和当前权限，最多 5000 条并防公式执行。

合同 / 回款文件复用私有附件服务，单文件最多 5MB。经通用附件入口也需满足当前合同、回款、客户及商机权限；通用客户附件选为财务凭证后绑定合同 / 回款访问范围。签订后的合同附件、已用于到账或冲正的凭证禁止删除。合同读取不含回款读取时，已收、未收和期次已收字段隐藏。

关键动作记录业务版本与审计，检查 CSRF、当前企业、幂等键和版本，按企业序列化关键写入。到期仅可受控读取，暂停企业拒绝访问。Flyway 新增 V8 / V9：50 张公开模式表、34 张企业范围表强制 RLS；运行与迁移账号独立，五类商业历史表不给运行账号 UPDATE / DELETE。

## 验证与备份

一次性原生 PostgreSQL 18.6 中完成 P0～P2-B 的 598 项回归、P2-C 58 项、P2-D 82 项及 11 项最终检查，共 749 项。覆盖异人确认、并发超收、凭证重复、冲正 / 更正链、角色撤销、字段隐藏、附件范围、历史不可改写、故障回滚及 RLS。Java 44 项、前端业务与金额 21 项、备份运维 17 项通过；类型检查与生产构建通过。

独立加密备份及完整恢复验证 50 张表、1890 行、34 张强制 RLS 表、9 次迁移、17 张商业表内容摘要、两份回款凭证。S3 回读、认证解密、篡改拒绝、附件内容及恢复后运行角色无上下文不可读均通过。

备份校验发现旧 P1-D 验收脚本清理临时对象时企业代码条件顺序不一致，导致已删除测试对象仍标为 READY。已修复清理条件；原预览未涉及该修正。备份没有忽略缺失文件，首次校验正确拒绝不完整快照；修复临时记录后完整恢复通过。

2026-10-14 凌晨原预览 V7 定时备份与独立恢复成功。每日北京时间 02:00 调度保留，程序升级支持 V5～V9 的精确表集合，保留 30 天并保护最近 3 份成功备份。原专用连接、密钥、对象及审计保留。升级后的 V9 首次实际定时执行待观察；独立密钥交接、异地副本、外部告警、正式 SMTP 和真实客户试点尚未完成。

浏览器视觉 / 鼠标 / 移动设备端到端、性能压测、真实邮件投递和生产恢复未执行；并发功能检查不等同于压力测试。当前仍是云测试版。

## 下一阶段

整体为 P0～P4 共五个大阶段，P1、P2 各分 A～D。本轮完成 P2-C / D，后续进入 P3：服务工单、SLA、知识库、营销与系统集成，建议先拆分 P3-A 服务工单与 SLA。P4 为行业配置、客户门户和 AI。正式邮件、密钥交接与客户试点继续作为上线准备事项推进。
